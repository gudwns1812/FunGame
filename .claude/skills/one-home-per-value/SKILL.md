# 값의 집은 하나다

**남이 소유한 가변 값은 복사해 담지 않는다. 식별자만 들고, 내보내는 경계에서 해석한다.**

값을 복사하는 순간 그 사본은 원본과 따로 늙는다. 원본이 바뀌어도 사본은 모른다.
바로 그때는 멀쩡해 보이고, 며칠 뒤 "로그아웃해야 반영된다"는 제보로 돌아온다.

## 1. 먼저 물을 것 — 스냅샷인가, 참조인가

복사가 틀린 게 아니다. **의도가 둘 중 어느 쪽인지**가 전부다.

| | 참조 (식별자만 든다) | 스냅샷 (값을 복사한다) |
|---|---|---|
| 원하는 것 | **지금** 값 | **그때** 값 |
| 원본이 바뀌면 | 따라 바뀌어야 한다 | 바뀌면 안 된다 |
| 예 | 채팅에 뜨는 보낸 사람 이름, 대기실 참가자 목록, 방 제목 | 영수증에 찍힌 상품명·가격, 감사 로그, 보낸 메일 본문 |
| 담는 것 | `memberId` | `nicknameAtThatTime` 처럼 **이름으로 시점을 박아둔다** |

스냅샷이라면 그렇게 보이게 이름을 짓는다. `nickname` 이라고만 적힌 필드는 읽는 사람이
전부 "지금 닉네임"으로 읽는다. 그 오해가 버그의 절반이다.

판단이 서지 않으면 이렇게 물어본다 — **"원본을 고친 사람이 이 화면을 보면 바뀌어 있어야 하나?"**
그렇다면 참조다.

## 2. 설계 레시피

1. **도메인 객체는 식별자만 든다.** `GamePlayer(memberId, isReady)` 이지 `(memberId, nickname, isReady)` 가 아니다.
2. **해석은 가장 바깥에서 한 번.** 응답을 조립하거나 이벤트를 내보내는 지점에서 식별자 → 값으로 바꾼다.
   도메인 안쪽으로 조회를 끌고 들어가면 계층이 꼬이고 테스트가 무거워진다.
3. **해석 비용이 I/O 면 캐시를 둔다.** 키는 식별자, 값은 **공개해도 되는 필드만** 담은 작은 레코드.
   원본을 고치는 곳에서 캐시도 같이 갱신한다(write-through). 갱신 지점이 한 곳이어야 이게 가능하다.
4. **목록은 한 번에 해석한다.** 단건 조회를 리스트에서 돌리면 N+1 이 된다. 없는 것만 모아 한 번에 읽는다.

해석을 경계에서 하면 **응답 JSON 모양은 그대로** 둘 수 있다. 값을 서버가 조립해 내려주므로
클라이언트는 아무것도 몰라도 된다. 리팩터링 비용이 거기서 크게 줄어든다.

## 3. 냄새 — 리뷰에서 이걸 본다

- **같은 필드 이름이 세 타입 이상에 보인다.** `nickname` 이 `Member`, `GamePlayer`, `Participant`,
  `ChatPayload` 에 전부 있으면 이미 퍼진 것이다.
- **생성자가 `(id, 그 id 로 조회되는 값)` 을 함께 받는다.** `createPlayer(memberId, nickname)` 는
  호출자에게 "지금 값을 떠서 넣어라"고 시키는 모양이다. 호출자마다 뜨는 시점이 달라진다.
- **두 필드가 서로 다른 출처에서 채워진다.** 한 DTO 의 `memberId` 는 세션에서, `nickname` 은
  방 객체에서 온다면 둘은 언제든 어긋날 수 있다.
- **세션·토큰·소켓 연결에 값이 실려 있다.** 핸드셰이크 때 박힌 값은 연결이 끊길 때까지 그대로다.
  "로그아웃해야 반영된다"는 제보는 거의 항상 여기다.
- **값 자리에 다른 뜻을 끼워 넣는다.** 사람이 아닌 줄을 그리려고 `nickname` 자리에 "성공" 같은
  문구를 넣고 `memberId` 를 `null` 로 두는 식. 자리가 모자라서 빌려 쓴 것이고, 나중에
  그 필드를 손대면 엉뚱한 곳이 깨진다. 뜻이 둘이면 타입을 나눈다.
- **부분집합 타입이 필드를 베껴 간다.** 아래 5절.

## 4. 이미 퍼진 값을 걷어내는 순서

1. **필드를 지운다.** 남겨두면 다음 사람이 또 채운다. 컴파일러가 모든 사용처를 짚어준다 —
   이게 가장 믿을 만한 목록이다.
2. 깨진 자리를 **바깥에서 안쪽 순으로** 메운다. 응답·이벤트 조립부터 해석을 붙이고,
   도메인 깊은 곳은 식별자만 들고 올라오게 바꾼다.
3. **테스트의 기대값을 이름에서 식별자로** 옮긴다. `extracting(nickname).containsExactly("방장")` 은
   `extracting(memberId)` 가 된다. 이름을 확인하고 싶은 테스트는 해석 지점에서 따로 쓴다.
4. 지우는 김에 **그 필드에 기대던 다른 의미**가 없는지 본다. null 여부로 "존재했는가"를
   판단하던 코드가 섞여 있으면 그건 별도 플래그로 꺼낸다.

작업이 넓어 보여도 대부분 기계적이다. 겁내서 필드를 남기는 쪽이 더 비싸다.

## 5. 부분집합 타입은 중복이 아니라 합성으로

공개용 좁은 타입을 따로 두는 것은 **옳다**. 남에게 나가는 값과 본인에게만 돌려주는 값은
공개 범위가 다르고, 좁은 타입이 그 사고를 구조적으로 막는다. 캐시나 외부 저장소로
직렬화되는 값이라면 더욱 그렇다.

틀린 건 **같은 필드를 양쪽에 적어두는 것**이다.

```java
// 이러면 nickname 이 두 집을 갖는다
record MemberInfo(Long id, String loginId, String nickname, String email, Role role) {}
record MemberProfile(Long memberId, String nickname, Role role) {}

// 넓은 쪽이 좁은 쪽을 품는다. nickname 의 집은 하나다
record MemberProfile(Long memberId, String nickname, Role role) {}
record MemberInfo(MemberProfile profile, String loginId, String email) {
    public Long id() { return profile.memberId(); }
    public String nickname() { return profile.nickname(); }
}
```

접근자가 한 겹 깊어지는 게 걸리면 **위임 메서드를 둔다.** 호출부는 `info.nickname()` 그대로
쓰면 되고, 값이 어디 사는지는 타입 안에서만 안다.

## 6. 예외 — 복사가 맞는 경우

- **시점을 보존해야 할 때.** 1절의 스냅샷. 이름에 시점을 드러낸다.
- **원본이 사라져도 남아야 할 때.** 탈퇴한 회원의 과거 기록 등. 다만 이것도 스냅샷이라고
  이름 붙인다.
- **값이 불변일 때.** 바뀌지 않는 값은 사본이 늙지 않는다. 다만 "지금은 안 바뀐다"와
  "앞으로도 안 바뀐다"는 다르다. 닉네임은 거의 항상 후자가 아니다.
- **해석 비용이 정말 문제일 때.** 먼저 캐시를 보고, 그래도 안 되면 복사하되 **갱신 경로를
  함께 설계한다.** 갱신 경로 없는 복사는 그냥 버그를 미루는 것이다.

## 7. 이 지침이 보는 축은 하나뿐이다

여기서 다루는 건 **값의 소유권** 하나다. 리뷰에는 다른 축이 함께 있다 — 성능, 수명과 주기,
비용, 실패 대비, 자료구조. 소유권 문제를 찾았다고 거기서 멈추면 더 큰 문제를 지나친다.

캐시를 예로 들면, "TTL 동안 옛 이름이 서빙된다"는 소유권 축의 지적이다. 같은 TTL 이
**데이터가 변하는 주기와 맞는지**는 비용 축의 질문이고, 둘은 별개다. 주 1회 집계하는 데이터에
1시간 TTL 이 걸려 있으면 소유권과 무관하게 그 자체로 낭비다.

소유권 판단을 마친 뒤 **"다른 축에서 볼 건 없나"를 한 번 더 묻는다.**

## 8. 새 필드를 달기 전에 — 한 문장 점검

> 이 값의 원본은 어디 있고, 거기서 바뀌면 여기도 바뀌어야 하나?

바뀌어야 한다면 들지 말고 식별자를 든다. 바뀌면 안 된다면 이름에 그렇게 적는다.
둘 다 아니면 아직 설계가 안 끝난 것이다.
