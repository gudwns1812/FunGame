# 브로드캐스트 스트림을 방별로 쪼개는 시점

작성일: 2026-10-05
관련: [스케일아웃 실행 계획](20260928-scale-out-multi-instance.md) 3단계, PR #90

인스턴스 간 STOMP 전파를 Redis Streams 로 깔면서 **스트림을 하나로 둘지 방마다 둘지**를 정해야 했다.
지금은 하나로 두었고, 이 문서는 **왜 지금은 하나이고 언제 쪼개는지**를 적는다.

## 지금

전역 스트림 `fungame:broadcast` 하나에 목적지를 필드로 싣는다.

```
instance / destination / user / payload
```

모든 인스턴스가 모든 메시지를 읽고, 자기가 보낸 것은 `instance` 로 걸러내고, 나머지를 자기
로컬 브로커에 흘린다. 블로킹 읽기는 인스턴스당 하나다.

## 방별 키로 가면 좋아지는 것

- **읽는 양이 준다.** 인스턴스가 자기 구독자를 들고 있는 방만 읽는다. 지금은 모든 인스턴스가
  모든 방의 메시지를 역직렬화한다.
- **트림이 방 단위다.** 긴 게임이 짧은 게임의 보관 구간을 밀어내지 않는다.
- **엔트리 id 가 곧 방별 순번이다.** 중복 제거용 번호를 따로 만들 필요가 없다.
  Streams 는 at-least-once 라 같은 메시지가 두 번 올 수 있고, 그때 클라이언트가
  `ROUND_START` 를 다시 받으면 카운트다운이 되감긴다.

## 대가

- **구독을 동적으로 관리해야 한다.** `XREAD` 는 키 목록을 고정해놓고 블로킹한다. 방이 생기고
  사라질 때마다 구독을 걸고 취소해야 하며 폴링 태스크가 그만큼 늘어난다.
- **"내가 어느 방의 구독자를 들고 있는가" 를 알아야 하는데 그 레지스트리가 없다.**
  `StompSessions` 는 회원과 세션만 들고 있고, `RoomSubscriptionAuthorization` 이 SUBSCRIBE 를
  보긴 하지만 기록하지 않는다. 새로 만들어야 하고, **구독 등록이 한 번 새면 그 방만 조용히
  메시지를 못 받는다.**
- **비방 스트림이 따로 필요하다.** 로비 목록 · 접속자 · 초대는 방 단위가 아니다. 메커니즘이 둘이 된다.

## 그래서 언제

**3단계의 방 소유권을 붙일 때 함께 쪼갠다.**

소유권이 생기면 "이 인스턴스가 어느 방을 맡는가" 가 이미 있다. 위에서 가장 비싼 대가였던
구독 레지스트리가 그 부산물로 따라오므로, 그때 쪼개는 것이 지금 쪼개는 것보다 싸다.

그 전에 다음 중 하나가 먼저 오면 그때 다시 본다.

- 동시 진행 방이 수백 개로 늘어 역직렬화가 지표에 보일 때
- 한 방의 폭주가 다른 방의 보관 구간을 밀어내는 것이 관측될 때
- 중복 전달로 클라이언트 화면이 되감기는 것이 실제로 보고될 때

## 쪼갤 때 할 일

- [ ] 인스턴스별 방 구독 레지스트리. `RoomSubscriptionAuthorization` 이 보는 SUBSCRIBE 와
      `WebSocketEventListener` 가 보는 연결 종료를 함께 반영해야 한다
- [ ] 방 스트림 키 `fungame:broadcast:room:{roomId}` 와 비방 스트림 `fungame:broadcast:global` 분리
- [ ] 구독이 생기고 사라질 때 `StreamMessageListenerContainer` 구독을 걸고 취소
- [ ] 엔트리 id 를 클라이언트까지 실어 중복 제거에 쓴다
- [ ] 구독 등록 누락을 드러낼 지표. 방별 수신 건수가 0 인 채로 유지되는 것을 볼 수 있어야 한다

## 하지 않을 것

- **소비자 그룹.** 그룹은 한 메시지를 그룹 안 한 소비자에게만 주는 작업 분배용이고 우리는
  팬아웃이 필요하다. 방별로 쪼개도 이 판단은 바뀌지 않는다.
- **방마다 Redis 커넥션 하나.** 커넥션 수가 방 수를 따라가면 안 된다. 한 컨테이너가 여러
  구독을 나눠 가지는 형태로 둔다.
