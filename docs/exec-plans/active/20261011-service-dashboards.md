# 실행 계획: 로그 수집을 되살리고 대시보드를 서비스 기준으로 다시 짠다

작성 2026-10-11
대상: `backend`(지표 · alloy) · `infra`(그라파나 대시보드)

이 문서가 유일한 계획이다. **남은 일만 적는다.** 끝난 작업은 지우고 코드와 커밋에 맡긴다.

---

## 1. 배경

2026-10-09 장애 때 대시보드로는 아무것도 볼 수 없어 서버에 직접 들어가야 했다.

- **로그가 10/7 부터 Loki 에 없다.** 블루그린 전환(#108)으로 컨테이너 이름이 `fungame-backend` 에서
  `fungame-backend-blue` · `-green` 으로 바뀌었는데, 앱 서버의 alloy 는 옛 이름만 수집한다.
  Loki 의 `container` 라벨에 blue · green 이 없는 것을 확인했다.
  alloy 설정은 저장소에 없고 서버에만 있어 이름이 바뀔 때 아무도 몰랐다.
- **응답시간 · 오류율 · 처리량을 한 화면에서 볼 수 없다.** 지금 대시보드는 브로드캐스트 · 로그인 ·
  "한 대의 한계" 처럼 기능별로 흩어져 있고, HTTP 요청 지표는 어디에도 없다.
  `http.server.requests` 히스토그램이 꺼져 있어 p95 · p99 를 낼 수도 없다.
- **장애의 직접 신호가 지표에 없다.** "트래픽을 받는 인스턴스 0대", "DB 커넥션 풀 고갈",
  "컨테이너 재시작" 을 보여 주는 패널이 없었다.

## 2. 결정

### 2.1 대시보드는 "무엇이 궁금한가" 로 나눈다

첫 화면 하나에서 서비스가 정상인지 판단하고, 이상하면 아래 상세 대시보드로 내려간다.
모든 대시보드는 같은 변수(`datasource` · `namespace` · `instance`)를 쓰고 서로 링크한다.

| 폴더 | 대시보드 | 답하는 질문 |
| --- | --- | --- |
| `FunGame` | **서비스 개요** | 지금 정상인가? (처리량 · 오류율 · 응답시간 · 받는 인스턴스 수 · 접속자 · ERROR 로그) |
| `FunGame` | API | 어느 엔드포인트가 느리거나 실패하나? |
| `FunGame` | 실시간 · 게임 | 방 · 게임 · STOMP 세션 · 라운드 타이머 · 브로드캐스트 전파가 괜찮나? |
| `FunGame` | 의존성 (DB · Redis) | MySQL 커넥션 풀 · 대기 · 타임아웃, Redis 명령 지연, 서킷 브레이커 |
| `FunGame` | 인프라 (JVM · 호스트) | 힙 · GC · 스레드, 컨테이너 메모리 대비 768m 제한, 호스트 CPU · 메모리 · 디스크, 재시작 |
| `FunGame` | 사용자 | 로그인 성공 · 실패, DAU |
| `FunGame` | 로그 | 인스턴스 · 레벨 · 검색어로 로그 보기 |

기존 대시보드 셋(브로드캐스트 · 로그인과 DAU · 한 대의 한계)과 로그 대시보드는 위 구성에
흡수하고 지운다. 폴더 `Logs` · `Metrics` 는 `FunGame` 하나로 합친다.

### 2.2 서비스 개요의 패널

| 줄 | 패널 |
| --- | --- |
| 상태 | 트래픽을 받는 인스턴스 수(0 이면 빨강) · 인스턴스별 가동 시간(재시작 감지) · 처리량(req/s) · 5xx 비율 · p95 응답시간 · ERROR 로그 수 |
| 요청 | 처리량 · 오류율 · 응답시간 p50/p95/p99 시계열, 인스턴스별 |
| 사용 | 접속 회원 · STOMP 세션 · 활성 방 · 진행 중 게임 |
| 의존성 요약 | DB 커넥션 사용 중 · 대기, 커넥션 획득 시간, Redis 명령 평균 · 최대 |

Hikari 획득 시간과 Lettuce 명령 시간은 히스토그램 없이 평균 · 최대만 나온다. 백분위가 필요해지면 그때 켠다.

방 · 게임 · 방 안 인원 · 접속 회원은 Redis 의 공유 상태를 읽어 **모든 인스턴스가 같은 전체 값을 보고한다.**
옛 대시보드는 이것을 `sum` 해 두 배로 보였다. 새 대시보드는 `max` 로 본다. STOMP 세션만 인스턴스마다 따로라 `sum` 한다.

### 2.3 앱에 더할 지표

- `http.server.requests` 히스토그램을 켠다. 응답시간 백분위를 내려면 버킷이 필요하다.
  버킷 수가 시계열 수를 늘리므로 SLO 버킷(예: 50ms · 100ms · 300ms · 1s · 3s)만 둔다.
- `fungame.traffic.accepting` 게이지(받으면 1, 아니면 0)를 인스턴스마다 낸다.
  10/9 장애에서 이 값이 둘 다 0 이었다.
- HikariCP · Lettuce · JVM · 프로세스 · logback 지표는 스프링 부트가 이미 내므로 더하지 않는다.
  Lettuce 명령 지표가 실제로 나오는지는 구현 때 `/actuator/prometheus` 로 확인한다.

### 2.4 alloy 설정을 저장소로 가져온다

- 서버에 있는 지금 설정을 받아 `backend/alloy/config.alloy` 로 옮기고, 컨테이너 선택 규칙을
  `fungame-backend` 로 **시작하는** 이름 전부로 바꾼다.
- 로그에 `instance`(blue · green) 라벨을 붙인다. 로그 패턴에 이미 `[blue]` 가 찍히므로 컨테이너 이름에서 뽑는다.
- alloy 를 `backend/compose.yml` 에 넣어 배포가 설정과 함께 올리게 한다. 지금은 compose 밖에서 8주째 떠 있다.
  배포의 별도 단계가 compose 밖의 옛 `alloy` 를 내리고 새 것을 띄운다. 이 단계가 실패해도 앱 배포는 실패로 치지 않는다.
- Loki 주소는 fungame-infra 의 사설 IP 로 설정에 직접 적는다. 3100 은 밖에서 막혀 있고 같은 VPC 안에서만 닿는다.
- 컨테이너는 `discovery.relabel` 에서 먼저 거른다. `loki.source.docker` 의 `relabel_rules` 로 거르면 라벨만 비고
  다른 컨테이너 로그도 라벨 없는 스트림으로 보낸다(로컬에서 재현).

### 2.5 그라파나는 배포 때 다시 띄운다

그라파나는 대시보드 프로바이더 목록을 기동할 때만 읽는다. 파일만 바꾸면 옛 대시보드가 그대로 남는 것을
로컬에서 확인했다. `deploy-infra.yml` 이 매번 그라파나를 다시 띄우고, 그러면 목록에서 빠진 프로바이더의
대시보드도 지워진다. 빈 `Logs` · `Metrics` 폴더는 남으니 배포 뒤 UI 에서 지운다.

### 2.6 하지 않는 것

- MySQL · Redis 서버 자체 지표(mysqld_exporter 등). 앱 쪽 커넥션 풀 지표로 먼저 본다.
- 컨테이너 단위 지표(cAdvisor). 재시작은 `process_start_time_seconds` 로 본다.
- 알림. 대시보드가 자리 잡은 뒤 따로 정한다(§4).

## 3. 단계 — PR 하나

PR 수를 늘리지 않으려고 앱 지표 · alloy · 대시보드를 한 PR 로 낸다. 대시보드가 먼저 배포돼도
새 지표 패널이 잠깐 비어 있을 뿐이다.

1. **앱 지표** — 테스트 먼저. `fungame.traffic.accepting`, `http.server.requests` SLO 버킷.
2. **alloy** — `backend/alloy/config.alloy`, compose 서비스, 배포 단계. 로컬에서 가짜 blue · green 컨테이너로
   라벨(container · instance · level)과 스택 트레이스 묶음, 다른 컨테이너 제외를 확인한다.
3. **대시보드** — 일곱 개 JSON, 프로비저닝 한 폴더, 옛 JSON 삭제, 인프라 배포의 그라파나 재시작.
   로컬 그라파나 · 프로메테우스 · Loki 로 쿼리 문법과 실제 지표에서 값이 나오는지 확인한다.
4. **머지 뒤 확인** — Loki 에 `fungame-backend-blue` · `-green` 이 들어오고, 프로메테우스에 새 지표가 보이고,
   그라파나에 `FunGame` 폴더 하나만 남는다.
