# 실행 계획: 공동 순위를 매기고 판 결과를 전적으로 남긴다

작성 2026-10-09
대상: `backend` `frontend`

이 문서가 유일한 계획이다. **남은 일만 적는다.** 끝난 작업은 지우고 코드와 커밋에 맡긴다.

---

## 1. 결정

### 1.1 동점이면 같은 순위다

지금은 점수가 같으면 `memberId` 가 작은 사람, 즉 먼저 가입한 사람이 앞 순위를 받는다. 결과 화면도 정렬 순서대로
`idx + 1` 위를 붙여 같은 점수가 1위와 2위로 갈린다. 공정하지 않다.

- 점수가 같으면 같은 순위다. 다음 순위는 그 인원만큼 건너뛴다. 10 · 10 · 7 점이면 1 · 1 · 3 위다.
- 순위는 백엔드 `GameRank` 한 곳에서 매긴다. 결과 화면과 전적이 같은 순위를 쓴다.
- 같은 순위 안의 표시 순서는 지금처럼 `memberId` 로 고정한다. 순위에는 영향이 없다.

### 1.2 승패는 결과에서 계산하고, 원본을 저장한다

승수 칸을 올리지 않는다. 판마다 참가자별 결과를 남기고 요약은 조회할 때 집계한다.

| 게임 | 승리 | 패배 |
| --- | --- | --- |
| 노래 퀴즈 · CS 퀴즈 | 끝까지 남은 1위 (공동 포함) | 나머지, 탈주자 |
| 행맨 (협동) | 성공 시 끝까지 남은 전원 | 실패 시 전원, 탈주자 |

- 탈주자는 점수와 상관없이 끝까지 남은 사람들보다 아래 순위이고 패배다.
- 1위 점수가 0 점이면(아무도 못 맞힘) 승자가 없다. 결과 화면에는 전원 공동 1위로 보이지만 전적은 전원 패배다.
- 시작 인원이 1명인 판은 기록하지 않는다.

### 1.3 같은 판은 한 번만 저장한다

`SHOW_RESULT` 예약 작업은 점유 기한(`GameTimer.LEASE`)이 지나면 다른 인스턴스가 다시 실행한다. 판을 시작할 때
판 id 를 만들어 스냅샷에 넣고 DB 에 고유 제약을 건다. `roomId` 는 판이 바뀌어도 같아 쓸 수 없다.

### 1.4 저장이 실패해도 판은 끝난다

지금의 `try { 결과 발행 } finally { endGame }` 원칙을 저장에도 적용한다. 저장 실패는 로그로 남기고 방을 풀어 준다.

### 1.5 하지 않는 것

- 판별 상세 기록 화면. 이번에는 전적 요약만 만든다.
- 레이팅 · 점수 누적 같은 다른 지표.

## 2. 1단계 — 공동 순위 (먼저 PR)

`main` 에서 새 브랜치 `feat/shared-rank` 를 딴다.

### 2.1 백엔드

1. **테스트 먼저** — `GameRankTest`
   - 동점자는 같은 순위를 받는다.
   - 동점 다음 순위는 인원만큼 건너뛴다 (10 · 10 · 7 → 1 · 1 · 3).
   - 전원 0 점이면 전원 1 위다.
2. `PlayerScore` 에 `rank` 를 더하고 `GameRank.getPlayerScores()` 가 정렬 뒤 순위를 매긴다.
3. `ResultRow` 에 `rank` 를 싣는다. 행맨의 `labelled` 행은 순위가 없다.
4. 내보내는 곳 두 군데에 `rank` 를 더한다.
   - `GameNotifier.toRankingPayload` — `GAME_RESULT` 의 `rankings[].rank`
   - `PlayerScoreResponse` — `GET /game/rooms/{roomId}/play/rank`
5. 명세 갱신
   - `api/websocket.md` 의 `GAME_RESULT` 설명은 이미 틀렸다(줄바꿈 문자열이라고 적혀 있다). 실제 배열 형태와 `rank` 로 고친다.
   - `api/game.md` 의 `PlayerScore` 에 `memberId` `rank` 를 적는다.

### 2.2 프론트엔드

1. **테스트 먼저** — 점수 목록에 공동 순위를 매기는 유틸 `withSharedRanks` 와 결과 화면의 vitest
2. 결과 화면(`Result.tsx`)과 진행 중 순위 목록(`RankingList.tsx`)이 같은 유틸로 순위를 매긴다. 공동 1 위는 둘 다
   1 위 배지를 받고, 우승 카드는 "공동 우승" 으로 모두의 이름을 보인다.
3. 서버가 주는 `rank` 를 쓰지 않고 점수로 다시 매긴다. 진행 중 목록은 점수를 클라이언트가 갱신하니 어차피 계산이
   필요하고, 결과 화면까지 같은 유틸을 쓰면 프론트와 백엔드의 배포 순서에 기대지 않는다. 규칙은 `GameRank` 와 같다.

### 2.3 확인

- `./gradlew :backend:core:core-api:test` 중 단위 테스트, `npm test`, `npm run build`
- testcontainers 통합 테스트는 이 PC 에서 안 도니 CI 에서 본다.

## 3. 2단계 — 전적 저장과 요약 (1단계 머지 뒤)

1. **판 id** — 판을 시작할 때 만들어 `GameSnapshot` 에 넣는다. 배포 중 옛 스냅샷에는 없으니
   `StoredShapeCompatibilityTest` 로 읽기 호환을 확인하고, id 가 없는 판은 기록하지 않는다.
2. **결과 판정** — 순수 도메인 객체가 §1.2 규칙으로 참가자별 승패 · 순위 · 탈주 여부를 낸다. 테스트를 먼저 쓴다.
   행맨이 탈주자를 기억하는지(`HangmanQuiz.initPlayers` 이후) 먼저 확인한다.
3. **테이블** — Flyway 로 추가한다.
   - `game_record` — 판 id (고유), 게임 종류, 시작 · 종료 시각, 시작 인원
   - `game_record_player` — 판, 회원 id, 승패, 순위, 점수, 탈주 여부. `(member_id, game_type)` 조회 인덱스
4. **저장** — `QuizGameService.showResult` · `HangmanGameService.submitResult` 에서 결과 발행과 같은 자리에 둔다.
   고유 제약 위반은 이미 저장된 판으로 보고 넘어간다.
5. **조회 API** — 내 전적 요약. 게임 종류별 판수 · 승 · 패 · 승률. 명세를 `api/` 에 추가한다.
6. **프론트** — 전적 요약을 보여 줄 자리를 정한 뒤 붙인다.
