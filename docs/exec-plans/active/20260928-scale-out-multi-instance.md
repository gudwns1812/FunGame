# 실행 계획: 인스턴스 2대 이상으로 트래픽을 나눠 받는다

작성 2026-09-28 · 개정 2026-10-06
대상: `backend` 전체 + 배포 인프라

이 문서가 유일한 계획이다. 결정이 바뀌면 옛 문장을 남기지 말고 고친다. 단, **뒤집은 결정은
무엇을 왜 뒤집었는지 같은 자리에 적는다**(§1.3). 근거 없이 되돌려지는 것을 막기 위해서다.

## 1. 결정

### 1.1 방과 판 모두 Redis 가 원본이다. 주인은 없다 ★ 2026-10-06 뒤집음

**처음에는** 한 방의 상태(`GameRoom` · `GameSession` · 타이머)를 그 방을 만든 인스턴스의 힙에 두고,
다른 인스턴스로 온 명령은 주인에게 전달하려 했다. 채팅마다 직렬화하는 비용을 피하려는 것이었다.

**그다음 갈랐다.** 대기실(`GameRoom`)은 사람이 누를 때만 바뀌는 작은 값이라 Redis 로, 판(`GameSession`)만
시작한 인스턴스의 힙에 두기로 했다.

**그것도 버렸다.** 주인의 힙에 판을 두면 **주인이 죽을 때 그 판이 같이 죽는다.** 서버를 여러 대 두는
이유가 가용성인데, 판이 서버 한 대의 수명에 묶이면 그 이유가 사라진다. 상태를 들여다보니 판도 저장할 수 있는
값이었다 — 문제 목록과 현재 번호, 행맨의 글자 · 남은 기회 · 차례, 점수, 스킵 투표, 라운드 시작 시각.

그래서:

- **방과 판의 원본은 Redis 다.** `fungame:room:{id}` 해시 하나에 방 · 판 · version 을 둔다.
- **명령은 받은 인스턴스가 처리한다.** Redis 에서 읽고 → 지금의 도메인 규칙(`GameRoom`, `GameSession`,
  `*Quiz`)을 자바에서 적용하고 → **version 이 그대로일 때만 쓰는 Lua** 로 바꾼다. 다른 인스턴스가 먼저 썼으면
  다시 읽어 재시도한다. 분산 락을 쓰지 않는다.
- **이벤트는 쓰기가 성공한 뒤에만 낸다.** 재시도한 시도의 이벤트는 버린다.
- **주인이 없다.** 명령을 넘길 곳도, 인계할 판도 없다. 어느 인스턴스가 죽어도 남은 인스턴스가 다음 명령을 받는다.
- **타이머도 Redis 에 둔다**(§2 O4). 아무 인스턴스나 시각이 된 것을 가져가 실행한다.

대가:

- 채팅 한 줄마다 판을 읽는다(정답 판정에 상태가 필요하다). 수 KB JSON 을 읽고 푸는 데 1~3ms 다.
- 라운드 끝에 여럿이 동시에 맞히면 version 충돌로 재시도가 난다. 방 정원이 8명이라 감당할 크기다.
- 이벤트를 내는 인스턴스가 여럿이라 스트림 안의 순서가 쓰기 순서와 어긋날 수 있다. 방 상태 메시지는
  `version` 을 실어 클라이언트가 옛것을 버릴 수 있고, 라운드 이벤트는 앞 이벤트가 뒤 이벤트를 부르는 인과 관계라
  실제로 뒤집힐 일이 드물다.

### 1.2 팬아웃은 Redis Streams 가 `SimpleBroker` 사이를 잇는다

Pub/Sub 이 아니다. 이유가 여럿이다.

| | Pub/Sub | Streams |
|---|---|---|
| 구독이 끊긴 동안 | **영구히 잃는다.** 그때 클라이언트는 멀쩡히 붙어 있어 재동기화도 안 한다 | 보관 기간 안이면 따라잡는다 |
| 느린 소비자 | `client-output-buffer-limit pubsub` 를 넘으면 **Redis 가 연결을 끊는다.** 그 뒤로 조용히 전부 유실 | 뒤처질 뿐 |
| 구독·해지 | Redis 서버에 명령. 채널→구독자 맵을 서버가 들고 있다. **방마다 쪼개면 방이 생기고 사라질 때마다 왕복** | 서버에 상태가 없다. 내 다음 `XREAD` 키 목록만 바꾼다 |
| 패턴 구독 | `PUBLISH` 마다 모든 패턴을 순회한다 | 해당 없음 |
| 발행 비용 | 구독자 N 명에게 동기로 복사. 단일 스레드에서 O(N) | `XADD` 는 O(1), 읽기 부담은 읽는 쪽으로 분산 |
| 뒤처짐 관측 | **불가능.** 위치 개념이 없다 | 내 마지막 id 와 스트림 끝을 비교할 수 있다 |

방 상태 이벤트는 전체 스냅샷을 실어 다음 이벤트가 덮지만
**라운드 전환(`ROUND_START` · `ROUND_END` · `GAME_RESULT`)은 잃으면 복구 경로가 없다.**
Pub/Sub 이 나은 점도 있다 — 푸시라 지연이 낮고, 트림도 오프셋 관리도 필요 없다.

처리량과 지연은 선택 근거가 아니다. 로컬 실측에서 `PUBLISH` 149k rps · `XADD` 161k rps 로
차이가 없었고, 그 수치마저 개발 PC 의 raw 명령이라 직렬화와 t2.micro 경합이 포함된 우리 경로를
잰 것이 아니다.

- 전역 스트림 `fungame:broadcast` 하나에 목적지를 필드로 싣는다 (`instance` / `destination` /
  `user` / `payload`). 방마다 스트림을 파는 것은 §부록 A.
- 소비자 그룹을 쓰지 않는다. 그룹은 한 메시지를 그룹 안 한 소비자에게만 주는 작업 분배용이고
  우리는 팬아웃이 필요하다. ACK 가 추가로 막는 칸은 "읽은 뒤 처리 전 프로세스 사망" 하나뿐인데
  그 경우 그 인스턴스의 웹소켓도 같이 끊겨 클라이언트 재연결 재동기화가 덮는다.
- 기동 시 `$` 부터 읽는다. 과거를 재생하지 않고 오프셋도 저장하지 않는다.
- `MINID` 로 5분 보관하며 **정확 트림**한다. 근사 트림은 라딕스 노드 경계 단위라 작은
  스트림에서 아무것도 지우지 않는다. 안 자르면 `maxmemory` + `noeviction` 에서 발행이 실패한다.

### 1.3 전달은 전부 스트림을 경유한다 ★ 2026-10-05 뒤집음

**전에는 이랬다.** `send()` 가 로컬 브로커에 먼저 넣고 그다음 스트림에 실었다. 근거는 "Redis 장애가
전체 먹통이 아니라 전파만 끊김이 된다" 였고, 실제로 Redis 를 내려 확인했다 — 로컬 구독자는
그대로 받았다.

**그런데 인스턴스가 2대 이상이면 그게 장점이 아니다.** 한 방의 플레이어가 A·B 에 흩어져 있을 때
Redis 가 끊기면 A 의 플레이어는 라운드 3 을 보고 B 의 플레이어는 라운드 2 에 멈춘다. 아무도
장애인 줄 모른 채 게임 결과가 갈라진다. **조용히 갈라지는 것이 깨끗하게 멈추는 것보다 나쁘다.**

그래서 발행한 인스턴스도 자기가 보낸 것을 스트림에서 되받아 전달한다.

- 스큐가 0 이 된다. 퀴즈 라운드에서 이건 공정성 문제다.
- 스트림이 유일한 순서다. 로컬 순서와 원격 순서가 갈리는 경합이 사라진다.
- `convertAndSend` 를 부르는 곳이 코드 전체에 한 군데가 된다.

**전제**: Redis 가 분리된 믿을 수 있는 의존성이어야 한다(§2 R1). 같은 박스에 있는 동안에는
플립하지 않는다 — 인스턴스 한 대짜리 시스템이 이유 없이 약해진다.

**대가**:
- Redis 가 실시간 전체의 하드 의존성이 된다.
- 전달이 리더 스레드 하나로 모인다. 지금은 호출 스레드마다 병렬이다.
- 큐가 가득 찼을 때 **버리는 게 아니라 호출자를 막아야 한다.** 유일한 사본이라 버릴 수 없다.

### 1.4 전파는 전달 스레드를 막지 않는다

`spread()` 가 호출 스레드에서 동기로 돈다. Redis 가 *죽으면*(connection refused) 즉시 실패하지만
*멈추면*(응답 없음) `timeout: 2s` 를 꽉 채운다. 측정값이다.

```
POST /game/rooms/{id}/join    36ms → 2,038ms      (실패 로그가 io-18080-exec-3 에)
채팅 20건                    1,277ms → 10,747ms
```

`GameNotifier` 리스너 13 개 중 `@Async` 는 2 개뿐이라 나머지는 이벤트를 발행한 스레드에서 돈다.
Tomcat 요청 스레드, STOMP inbound, `game-timer-`, `app-sched-` 가 전부 해당된다.

전파는 best-effort 인데 전달 경로의 임계 구간에 들어가 있다. **연속 실패가 기준에 닿으면 막는다.**
`XADD` 는 그대로 동기로 두고, 멈춘 Redis 를 몇 번까지만 물고 그 뒤로는 건드리지 않는다.

바운디드 큐와 워커 스레드 하나로 떼어내는 안을 먼저 넣었다가 되돌렸다. 큐는 가용성을 올리지
않으면서(어차피 버린다) **워커가 하나라 `XADD` 를 직렬화해 초당 745건 천장을 만들었다**
(`1 / 1.34ms`, 실측 처리량 793/s 와 일치). Lettuce 가 커넥션 하나로 순서를 이미 지켜 주므로
직렬 워커는 라이브러리가 하는 일을 다시 만든 것이었다.

브레이커는 Resilience4j 를 쓴다. 직접 만든 것은 예외만 세서 **느리지만 성공하는 Redis** 를
영영 못 잡았다. `slow-call-duration-threshold` 로 0.5초를 넘긴 호출을 실패로 세면 그 상태도 잡힌다.
막기까지의 노출이 실측에서 `/join` 2.04초 **한 번**으로 줄었다(직접 만든 것은 두 번). 정상 상태 비용은 호출당 1.3ms 다. 접속자 목록 팬아웃이 뷰어당 1건이라
접속자가 많으면 이 1.3ms 가 N 배가 되는데, 그건 브레이커가 아니라 P0 으로 고친다.

### 1.5 명령을 다른 인스턴스로 넘기지 않는다

모든 인스턴스가 같은 원본(Redis)을 읽고 쓰므로 명령은 받은 곳에서 처리한다(§1.1). 주인에게 전달하는 경로,
그 경로의 루프 방지, 주인 사망 시 인계가 모두 필요 없다.

**절대 하지 말아야 할 것은 지금처럼 조용히 무시하는 것이다.** 방이나 판이 없으면 에러로 답한다.

### 1.6 하지 않는 것

| | 이유 |
|---|---|
| **경로 라우팅** (`/ws-quiz/{roomId}`) | 로비에 있는 사람은 roomId 가 없어 라우팅 키가 없다. 방에 들어갈 때마다 WS 를 끊고 다시 붙어야 한다. 로비·접속자·초대는 전역이라 팬아웃을 못 뺀다 |
| ~~**전면 공유 상태**~~ ★ 2026-10-06 뒤집음 | 처음에는 `GameSession` 이 `Quiz` 객체 그래프를 직접 변형해 직렬화 경계가 없고 방 수명이 짧아 인스턴스 장애로 한 판을 잃는 비용이 낮다고 보고 기각했다. 가용성을 이유로 뒤집었다(§1.1). 분산 락 · 외부 릴레이는 여전히 쓰지 않는다 — version 비교 쓰기로 한다 |
| **DB 로 전부 대체** | 1초 단위 접속 추적과 500ms 로비 팬아웃을 DB 폴링으로 하면 커넥션이 녹는다 |
| **RabbitMQ** | 아래 |

**RabbitMQ 를 안 쓰는 이유.** 우리가 필요한 건 팬아웃이지 경쟁 소비자가 아니다. Rabbit 으로 하면
exclusive·auto-delete 큐는 끊긴 동안 유실되고, durable per-instance 큐는 죽은 인스턴스의 고아 큐가
쌓여 TTL·max-length 정책과 청소를 직접 달아야 한다. Streams 는 키 하나에 트림 하나로 끝난다.
그리고 `basicPublish` 가 안 막히는 건 publisher confirms 를 버려서 얻는 것이라 `XADD` 보다 보장이
약하다. "브로커를 제대로 쓰면 §1.4 의 큐·워커가 사라진다" 는 것도 사실이 아니다 — 그건 브로커가
아니라 "네트워크 호출로 전달 스레드를 막지 마라" 에서 나온 요구다.

**다시 볼 조건** (하나라도 오면 재검토):

1. 진짜 경쟁 소비자 작업이 생기고 재시도·DLQ 가 필요할 때
2. 팬아웃 양이 리더 스레드 분할로도 안 될 때
3. 자바 아닌 소비자가 붙거나 라우팅이 복잡해질 때
4. 브로커를 따로 띄울 호스트가 생겼을 때

### 1.7 감수하는 것

- 인스턴스가 죽어도 **방과 판은 Redis 에 남는다.** 그 인스턴스에 붙어 있던 사람은 재접속해 이어 한다.
  죽기 직전에 쓰지 못한 한 번의 변경(예: 그 순간의 정답 한 건)만 잃는다.
- Redis 가 실시간과 게임 전체의 하드 의존성이다(§1.3 과 같은 대가).
- 배포할 때 드레인이 필요하다. 헬스체크를 liveness / readiness 로 나누지 않으면 드레인 중
  인스턴스가 재시작돼 진행 중 게임이 죽는다.
- **사용자 지정 메시지(`/queue/invite`)는 전달 여부를 알 수 없다.**
  전역 스트림을 모든 인스턴스가 읽고 그 사용자의 세션을 가진 쪽만 내보낸다. 나머지는 조용히
  버린다. 그래서 "전달됐다" 와 "그 사용자가 접속해 있지 않다" 와 "라우팅이 깨졌다" 가
  지표에서 똑같이 보인다. `received` 는 처리한 수지 전달한 수가 아니다.
  고치려면 둘 중 하나다 — 보내기 전에 공유 접속 상태(P1)를 보고 오프라인이면 발행하지 않거나,
  `broadcast:user:{id}` 키를 그 세션을 가진 인스턴스만 읽게 한다.

### 1.8 접속 상태는 연결 목록과 서버 생존 키로 판단한다 ★ 2026-10-06 뒤집음

**처음에는** 연결마다 30초 리스를 두고, 서버가 10초마다 자기 연결의 리스를 늘렸다. 죽은 서버의 연결이
저절로 빠지게 하려는 것이었다. 접속자 목록에는 마지막 연결이 끊겨도 20초 유예를 뒀다.

**버린 이유는 둘이다.**

- **리스 갱신이 방금 끊긴 연결을 되살린다.** 갱신은 서버 메모리에서 내 연결을 읽고 Redis 에 쓴다. 그 사이에
  끊김이 끼면 방금 지운 연결이 30초 리스로 다시 생긴다. 리스(30초)가 방 이탈 유예(15초)보다 길어서
  `RoomLeaveGrace` 는 "다시 접속했다" 고 보고 내보내지 않는다. 다시 확인하지도 않으니 그 회원은 방에 영원히 남는다.
  갱신이 Redis 가 키를 잃었을 때 되살리려고 `XX` 없이 쓰는 한, "Redis 가 잃은 연결" 과 "방금 끊긴 연결" 을
  구분할 수 없다.
- **목록 유예 20초는 이유가 사라졌다.** SSE 가 5분마다 강제로 끊기던 때(#28) 깜빡임을 가리려고 넣었는데,
  SSE 는 STOMP 로 옮기며 걷어냈다. 남은 쓸모는 새로고침 1~3초를 가리는 것뿐인데, 그 대가로 마감 점수를 든
  ZSET 과 1초 정리 작업을 들고 있었다.

**그래서 이렇게 한다.**

- 연결은 기한 없이 적고, 끊길 때 지운다. 연결마다 갱신하지 않는다.
- 살아 있음은 **서버 단위**로 알린다. 서버마다 키 하나만 연장하고 연결은 건드리지 않으므로, 끊긴 연결이
  되살아날 길이 없다.
- 죽은 서버의 연결은 "살아 있나" 를 물을 때 바로 걸러 내고, 살아 있는 서버가 치운다.
- 접속자 목록은 실제 연결이 있는 회원 그대로다. 유예가 없다.
- 방 이탈 유예(15초, `RoomLeaveGrace`)는 그대로다. 판단 근거만 위 연결 목록으로 바뀐다.

**대가는 이렇다.**

- 새로고침할 때 남의 접속자 목록에서 1~3초 사라졌다 나타난다.
- 죽은 서버에 붙어 있던 회원이 최대 40초(생존 키 30초 + 정리 주기 10초) 동안 목록에 남는다.
  "살아 있나" 판단에서는 생존 키가 사라지는 즉시 빠진다.
- Redis 가 재기동해 키를 잃으면 접속 상태가 빈다. 다시 접속하는 사람부터 채워진다. 서버 메모리의
  `StompSessionRegistry` 로 다시 채울 수는 있지만, 그건 끊긴 연결을 되살리는 경합을 다시 들이는 일이라
  생존 키가 사라진 것을 감지했을 때만 하는 안으로 남겨 둔다.

```
 ├─ N2 클래스 분리   ─┤          ┌─ R1 Redis 호스트 분리
 └─ N3 채팅 일원화   ─┘          │
                │                │
                └────────────────┴──▶ N4 전부 스트림 경유로 플립
                                            │
   ┌────────────────────────────────────────┤
   ▼                                        ▼
 P1 Presence · P2 Invite               O1 GameRoom → Redis
 P3 세션 Redis · P4 ShedLock                ├─▶ O5 구독 권한
                                            ▼
                                       O2 판을 저장 가능한 값으로
                                            ▼
                                       O3 GameSession → Redis
                                            ▼
                                       O4 타이머 → Redis
                                            ▼
                                       O6 인스턴스 2개 검증
                 P1 · P3 · O1 ──────────────────────────▶ W1 모듈 분리
                                       O7 방별 스트림 키 (부록 A)
```

### 1단계 — 방송 경로

| | 작업 | 지금 생기는 일 |
|---|---|---|
| N6 | 보관 기간 추월 감지 — `내 마지막 id < 스트림 첫 id` | 5분보다 뒤처진 인스턴스가 조용히 틀어진다 |

### 2단계 — Redis 분리와 플립

| | 작업 | 지금 생기는 일 |
|---|---|---|
| N4c | 리더 스레드를 destination 해시로 N개 분할 | 전달이 `broadcast-1` 하나로 모인다. **지표가 한계를 보일 때만** |

### 3단계 — 공유 상태 (소유권 없이 되는 것)

| | 작업 | 2대에서 생기는 증상 |
|---|---|---|
| P3 | HTTP 세션 JDBC → Redis | 모듈 분리 선행. 그대로면 모듈이 인증 때문에 MySQL 세션 테이블을 읽어야 한다 |
| P4 | ShedLock 또는 리더 선출 | `fillPendingSongs` 가 클레임 없이 `findOldest(10)` 을 긁어 **유튜브 호출이 인스턴스 수만큼 늘고 차단 위험**이 있다(우선순위 높음). `deleteExpiredTokens` 도 전역 |

### 4단계 — 방과 판을 Redis 로 (§1.1)

| | 작업 | 2대에서 생기는 증상 |
|---|---|---|
| O0 | `INSTANCE_ID` 를 모든 로그·메트릭 라벨로 | 어느 인스턴스에서 난 일인지 구분이 안 된다 |
| O7 | 방별 스트림 키 | §부록 A |

### 5단계 — 인스턴스 2대 (같은 EC2, 컨테이너 2개)

**여기서 돈을 쓰지 않는다.** `backend-a` · `backend-b` 를 띄우고 Caddy 가 앞에서 나눈다.

| | 작업 | 지금 생기는 일 |
|---|---|---|
| C1 | `compose.yml` 을 백엔드 2개로, MySQL 포트를 사설로 | `ports: 3306:3306` 으로 **DB 가 인터넷에 열려 있다.** 보안 그룹이 유일한 방어선 |
| C2 | Caddy 쿠키 스티키 (`lb_policy cookie`) | SockJS XHR 폴백은 한 연결의 여러 요청이 같은 인스턴스로 가야 한다 |
| C3 | Flyway 단일 실행 또는 기동 순서 명시 | 동시에 뜨면 마이그레이션이 경합한다 |
| C4 | Prometheus 타깃을 인스턴스별로 | `instance` 라벨 없이는 대시보드가 의미가 없다 |
| C5 | 헬스체크 liveness / readiness 분리 | §1.7 |
| C6 | `deploy-backend.yml` 을 다중 인스턴스로 | `--no-deps backend`, `docker exec fungame-backend` 가 컨테이너 하나를 전제한다 |

**종료 조건** (5단계 컨테이너 구성에서 다시 확인한다. 같은 조건을 앱 수준에서는 O6 테스트가 이미 검사한다): A 에서 만든 방이 B 목록에 보이고 / B 로 들어온 정답이 처리되고 / A→B 재접속이
강제 퇴장당하지 않고 / 방 채팅이 양쪽 구독자에게 도달한다. **판이 도는 중에 한 인스턴스를 `docker kill` 해도
판이 다른 인스턴스에서 이어지고, 다음 라운드가 제시간에 온다.**

### 6단계 — websocket 모듈 분리

선행: P1 · P3 · O1

**연결은 모듈, 의미는 core.** 모듈은 게임을 모르고 core 는 STOMP 를 모른다.

| | 작업 |
|---|---|
| W1 | 모듈: 핸드셰이크 인증, `StompSessionRegistry`, 목적지 규칙, 구독 권한 조회, 스트림 수신·전달, 연결·끊김 이벤트 발행 |
| W2 | core: `*Notifier` 가 응답을 조립해 스트림에 넣는다. 끊김 유예·접속 상태·일일 활성처럼 연결이 도메인에서 갖는 의미는 core 가 판단한다 |
| W3 | 같은 회원이 여러 인스턴스에 붙었을 때 "마지막 세션이 끊겼는가" 판단을 모듈로 옮긴다. 기준은 §1.8 로 정했다 |

SSE + REST 안은 프런트를 다시 짜야 해서 기각했다.

### 7단계 — 실제 EC2 증설

**진입 조건**: 지표가 한 대의 한계를 증명했을 때만. "곧 유저가 늘 것 같다" 는 진입 조건이 아니다.
그전에 **t2.micro → t3.small 상향과 스레드 풀 튜닝을 먼저** 시도한다. 첫 한계는 1GB RAM 일
가능성이 가장 높고, 그건 설정이 아니라 돈이지만 서버를 늘리는 것보다 훨씬 싸다.

| | 작업 |
|---|---|
| E1 | MySQL 을 앱 호스트에서 분리 (전용 EC2 또는 RDS) |
| E2 | ALB + 타깃 그룹 2개, 스티키 쿠키 |
| E3 | TLS 종료를 Caddy → ALB. 앱은 평문 8080 만 |
| E4 | 보안 그룹: 8080·3306·6379 는 ALB / 앱 SG 에서만 |

**비용** — 프리티어에서 2대는 공짜가 아니다.

| 항목 | 프리티어 | 2대로 갈 때 |
|---|---|---|
| EC2 t2/t3.micro | 계정당 월 750시간 | 2대 = 1,440시간 → 절반 과금, 월 $8–9 |
| ALB | 12개월 750시간 + 15 LCU | 12개월 지나면 월 $16~ |
| ElastiCache micro | 12개월 750시간 | 기간 지나면 과금 |

**더 싼 선택지 둘**: EC2-app-1 의 Caddy 가 자기 자신과 app-2 로 나눈다(공짜지만 app-1 이 단일
장애점) / Cloudflare 무료 플랜에 오리진 2개(스티키가 유료라 **SockJS 폴백을 끄고 WebSocket 만**
쓰도록 프런트를 고정해야 한다).

| N1 · N2 · N5 | 전파가 멈춘 Redis 에 전달 스레드를 묶지 않게 했다. `XADD` 는 동기로 두고 Resilience4j 서킷 브레이커가 실패나 0.5초 넘는 느린 호출이 쌓이면 막는다(§1.4). `StompBroadcaster` 는 Redis 를 모른다. Grafana 에 `브로드캐스트 전파` 대시보드를 붙였다 |

검증한 것: Redis 를 내려도 로컬 전달이 유지된다(실제 구독자로 확인). 복구는 자동이지만 Lettuce
재연결 전 한 건은 유실된다. 멈춘 Redis 는 죽은 Redis 보다 나쁘다(§1.4).

## 부록 A. 방별 스트림 키

지금은 전역 스트림 하나에 목적지를 필드로 싣는다. **방 소유권(O2)을 붙일 때 함께 쪼갠다.**

쪼개면 좋아지는 것:

- 인스턴스가 자기 구독자를 들고 있는 방만 읽는다. 지금은 모든 인스턴스가 모든 방의 메시지를
  역직렬화한다. **N4 이후에는 전달까지 리더 스레드가 하므로 이 비용이 더 커진다.**
- 트림이 방 단위라 긴 게임이 짧은 게임의 보관 구간을 밀어내지 않는다.
- 엔트리 id 가 곧 방별 순번이다. Streams 는 at-least-once 라 같은 메시지가 두 번 올 수 있고,
  그때 클라이언트가 `ROUND_START` 를 다시 받으면 카운트다운이 되감긴다.

대가:

- `XREAD` 는 키 목록을 고정해놓고 블로킹한다. 방이 생기고 사라질 때마다 구독을 걸고 취소해야 한다.
- **"내가 어느 방의 구독자를 들고 있는가" 레지스트리가 없다.** 구독 등록이 한 번 새면 그 방만
  조용히 메시지를 못 받는다.
- 로비·접속자·초대는 방 단위가 아니다. `fungame:broadcast:global` 이 따로 필요하고 그건 모든 인스턴스가 읽는다. 메커니즘이 둘이 된다. **초대에는 roomId 가 없어서 방 키에 실을 수 없다.**
- 파티션 기준을 도메인 개념(roomId)에 두면 목적지 모양이 늘 때마다 다시 설계해야 한다. 1:1 DM 하나만 들어와도 키 체계가 또 생긴다. 도메인과 무관하게 가려면 `hash(destination) % N` 고정 샤드에 수신 측 로컬 필터(구독자 없으면 역직렬화 전에 버림)를 얹는 쪽이다 — 리스너 단일 스레드 병목도 같이 풀린다. **지금은 roomId 기준을 유지하고, 그런 요구사항이 실제로 오면 그때 바꾼다.**

소유권이 생기면 가장 비싼 대가인 구독 레지스트리가 부산물로 따라온다. 그래서 그때가 싸다.
그 전에 **동시 진행 방이 수백 개로 늘어 역직렬화가 지표에 보이거나 / 한 방의 폭주가 다른 방의
보관 구간을 밀어내거나 / 중복 전달로 화면이 되감기는 것이 보고되면** 그때 다시 본다.

쪼갤 때 할 일:

- [ ] 인스턴스별 방 구독 레지스트리. SUBSCRIBE 와 연결 종료를 함께 반영해야 한다
- [ ] `fungame:broadcast:room:{roomId}` 와 `fungame:broadcast:global` 분리
- [ ] 구독 생성·소멸에 맞춰 `StreamMessageListenerContainer` 구독을 걸고 취소
- [ ] 엔트리 id 를 클라이언트까지 실어 중복 제거에 쓴다
- [ ] 구독 등록 누락을 드러낼 지표. 방별 수신 0 이 유지되는 것을 볼 수 있어야 한다

**하지 않을 것**: 소비자 그룹(§1.2), 방마다 Redis 커넥션 하나(커넥션 수가 방 수를 따라가면 안 된다).
