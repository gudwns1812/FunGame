# 실행 계획: 인스턴스 2대 이상으로 트래픽을 나눠 받는다

작성 2026-09-28 · 개정 2026-10-07
대상: `backend` 전체 + 배포 인프라

이 문서가 유일한 계획이다. **남은 일만 적는다.** 끝난 작업은 지우고 코드와 커밋에 맡긴다. 결정이
바뀌면 옛 문장을 남기지 말고 고치되, **뒤집은 결정은 무엇을 왜 뒤집었는지 같은 자리에 적는다.**
근거 없이 되돌려지는 것을 막기 위해서다.

---

## 1. 결정

### 1.1 방과 판 모두 Redis 가 원본이다. 주인은 없다 ★ 2026-10-06 뒤집음

**처음에는** 방과 판을 그 방을 만든 인스턴스의 힙에 두고 다른 인스턴스로 온 명령을 주인에게 전달하려 했다.
그다음 대기실만 Redis 로, 판은 시작한 인스턴스의 힙에 두기로 갈랐다. **둘 다 버렸다.** 판이 서버 한 대의
힙에 있으면 그 서버가 죽을 때 판도 죽어, 서버를 여러 대 두는 이유(가용성)가 사라진다.

- 명령은 받은 인스턴스가 처리한다. 읽고 → 자바 도메인 규칙 적용 → revision 이 그대로일 때만 쓴다. 충돌하면 다시 읽는다.
  분산 락을 쓰지 않는다.
- 이벤트는 쓰기가 성공한 뒤에만 낸다.
- 타이머도 Redis 큐에 두고 아무 인스턴스나 시각이 된 것을 가져가 실행한다. 작업은 두 번 돌아도 안전해야 한다.

대가: 채팅 한 줄마다 판을 읽는다. 동시에 맞히면 revision 충돌로 재시도한다. 이벤트를 내는 인스턴스가 여럿이라
스트림 안의 순서가 쓰기 순서와 드물게 어긋난다.

### 1.2 팬아웃은 Redis Streams 가 잇는다. Pub/Sub 이 아니다

Pub/Sub 은 구독이 끊긴 동안의 메시지를 영구히 잃고, 느린 소비자는 Redis 가 연결을 끊어 조용히 전부 유실된다.
라운드 전환(`ROUND_START` · `ROUND_END` · `GAME_RESULT`)은 잃으면 복구 경로가 없다. 처리량은 선택 근거가 아니다.
소비자 그룹은 쓰지 않는다 — 필요한 건 작업 분배가 아니라 팬아웃이다.

### 1.3 전달은 전부 스트림을 경유한다 ★ 2026-10-05 뒤집음

**전에는** 로컬 브로커에 먼저 넣고 스트림에 실어 "Redis 장애가 전파만 끊는다" 를 얻었다. 인스턴스가 둘이면
그게 장점이 아니다 — Redis 가 끊기면 A 와 B 의 플레이어가 서로 다른 라운드를 보며 조용히 갈라진다.
**조용히 갈라지는 것이 깨끗하게 멈추는 것보다 나쁘다.** 발행한 인스턴스도 스트림에서 되받아 전달한다.

### 1.4 전파는 전달 스레드를 막지 않는다

멈춘 Redis(응답 없음)는 죽은 Redis 보다 나쁘다 — 호출마다 타임아웃을 꽉 채운다. `XADD` 는 동기로 두고
서킷 브레이커가 실패와 느린 호출이 쌓이면 막는다. 큐와 단일 워커로 떼어내는 안은 처리량 천장을 만들어 되돌렸다.

### 1.5 명령을 다른 인스턴스로 넘기지 않는다

모든 인스턴스가 같은 원본을 본다(§1.1). 방이나 판이 없으면 조용히 무시하지 말고 에러로 답한다.

### 1.6 하지 않는 것

| | 이유 |
|---|---|
| **경로 라우팅** (`/ws-quiz/{roomId}`) | 로비 · 접속자 · 초대는 전역이라 라우팅 키가 없다. 방에 들어갈 때마다 WS 를 다시 붙여야 한다 |
| **분산 락 · 외부 릴레이** | revision 비교 쓰기로 한다. 락을 쥔 인스턴스가 죽으면 TTL 동안 막힌다 |
| **DB 로 전부 대체** | 1초 단위 접속 추적과 500ms 로비 팬아웃을 DB 폴링으로 하면 커넥션이 녹는다 |
| **RabbitMQ** | 경쟁 소비자가 아니라 팬아웃이 필요하다. 인스턴스별 큐는 죽은 인스턴스의 고아 큐 청소를 직접 달아야 한다. 진짜 경쟁 소비자 작업 · 자바 아닌 소비자 · 별도 브로커 호스트가 생기면 다시 본다 |

### 1.7 감수하는 것

- Redis 가 실시간과 게임 전체의 하드 의존성이다.
- 인스턴스가 죽으면 죽기 직전에 쓰지 못한 한 번의 변경(그 순간의 정답 한 건)만 잃는다.
- 사용자 지정 메시지(`/queue/invite`)는 전달 여부를 알 수 없다. 모든 인스턴스가 읽고 그 세션을 가진 쪽만 내보내므로,
  "전달됐다" · "접속해 있지 않다" · "라우팅이 깨졌다" 가 지표에서 똑같이 보인다.

### 1.8 접속 상태는 연결 목록과 서버 생존 키로 판단한다 ★ 2026-10-06 뒤집음

**처음에는** 연결마다 리스를 두고 서버가 주기적으로 늘렸다. 갱신이 메모리에서 읽은 연결을 Redis 에 다시 쓰는
사이에 끊김이 끼면 **방금 끊긴 연결이 되살아나** 그 회원이 방에서 영영 빠지지 않았다. 그래서 연결은 끊길 때
지우고, 살아 있음은 서버 단위 생존 키로만 알린다. 접속자 목록 유예(SSE 시절 #28)는 이유가 사라져 없앴다.
접속 규칙은 Lua 가 아니라 자바에 둔다(`BACKEND.md` 8번).

### 1.9 함께 쓰는 것은 바로 앞 버전과 함께 돌 수 있어야 한다 (2026-10-07)

무중단 배포는 서버를 하나씩 바꾸므로 **몇 분 동안 옛 버전과 새 버전이 같은 Redis · DB 를 동시에 쓴다.**
지금 코드는 모든 서버가 같은 버전이라고 가정한다. 지금은 서버 1대를 내렸다 올려 버전이 섞이지 않지만,
5단계에 들어가면 바로 깨진다.

대상은 버전 사이에 오가는 모든 것이다.

| 대상 | 버전이 섞이면 |
|---|---|
| Redis 저장 형태 (방 · 판 · 퀴즈 스냅샷 JSON) | 필드 이름이나 enum 값을 바꾸면 상대 버전이 쓴 방을 못 읽는다. **못 읽는 방은 정리 작업이 지우므로 멀쩡한 방과 진행 중인 판이 사라진다** |
| Redis 키 구조 · 타이머 작업 종류 | 새 작업 종류를 옛 서버가 가져가면 해석에 실패해 함께 가져간 작업 묶음이 리스 동안 멈추거나, 처리기가 없어 지워진다 |
| DB 스키마 (Flyway) | 컬럼 이름을 바꾸거나 지우면 아직 도는 옛 서버의 쿼리가 실패한다 |
| 서버 간 브로드캐스트 메시지 | 형식이 바뀌면 상대 서버가 못 읽는다 |
| 프런트 ↔ 백엔드 API · 구독 주소 | 배포 시점이 어긋난 동안 깨진다 |

원칙은 **확장 후 축소**다. 새 형태를 "있어도 되고 없어도 되는" 것으로 먼저 추가해 한 번 배포하고, 옛 형태는
그다음 배포에서 지운다. 한 번의 배포로 형태를 바꾸지 않는다.

### 1.10 배포는 블루-그린이고, 내린 환경을 버리지 않고 같은 버전으로 올려 다시 합류시킨다 (2026-10-07)

롤링은 한 방의 라운드를 v1 이 열고 v2 가 닫게 한다. 그걸 견디려면 "방마다 시작한 버전의 규칙을 따라간다"
같은 장치가 규칙을 바꿀 때마다 붙는다. 블루-그린은 **한 방의 모든 명령이 트래픽 받는 쪽으로만 가서** 그게 필요 없다.
전환 뒤 내린 환경은 버리지 않고 새 버전으로 올려 풀에 다시 넣는다 — 평시 용량이 2대가 된다.

**다만 트래픽만 가르면 이 이점이 생기지 않는다.** 트래픽을 한 줄도 안 받는 인스턴스도 기동 즉시 같은 Redis 를
보고 `GameTimerPoller` 로 **상대 버전이 건 타이머를 가져가 제 규칙으로 실행하고**, `cleanupIdleRooms` 로 상대가
쓴 방을 본다. 그래서 **readiness 플래그가 블루-그린의 전제다** — 트래픽을 받기 전에는 타이머 폴링 · 방 정리 ·
스크래핑을 멈추고 읽기만 한다. 이게 없으면 이름만 블루-그린이고 공존 요구는 롤링과 같아진다.

§1.9 는 그대로 남는다. 혼재 창이 짧아져도 없어지지 않고, **롤백이 "v2 가 쓴 것을 v1 이 읽기" 를 강제한다.**

드레인은 기다리는 것이 아니다. 판이 도는 방의 WebSocket 은 몇 분씩 산다. **끊어서 재연결을 유도한다** —
프런트가 자동으로 다시 붙고, 새 연결은 전환된 쪽으로 가고, 판은 Redis 에 있어 `rejoinPlayingRoom` 이 잇는다.

## 2. 남은 일

```
 R1 readiness ────┐
 R2 드레인 ───────┤
 P4 ShedLock ─────┼──▶ 5단계 블루-그린 (C1~C6) ──▶ 7단계 실제 EC2 증설
 O0 인스턴스 라벨 ─┘
 P3 ──────────────────▶ 6단계 websocket 모듈 분리 (W1~W3)
 N6 · N4c · O7 은 지표가 요구할 때
```

**V1~V4 는 끝났다.** 못 읽는 방을 쓰인 시각으로만 지우고(`RoomStore.removeIdle`), 모르는 종류 · 처리기 없는
예약 작업을 완료 처리하지 않으며(`GameTimer` · `GameTimerPoller`), `StoredShapeCompatibilityTest` 가 저장
형태를 고정하고, `BACKEND.md` 9번이 "두 번에 나눠 바꾼다" 를 적는다.

### 3단계 — 공유 상태

| | 작업 | 2대에서 생기는 증상 |
|---|---|---|
| P3 | HTTP 세션 JDBC → Redis | 모듈 분리 선행. 그대로면 모듈이 인증 때문에 MySQL 세션 테이블을 읽어야 한다 |
| P4 | ShedLock 또는 리더 선출 | `fillPendingSongs` 가 클레임 없이 `findOldest(10)` 을 긁어 **유튜브 호출이 인스턴스 수만큼 늘고 차단 위험**이 있다(우선순위 높음). `deleteExpiredTokens` 도 전역 |
| O0 | `INSTANCE_ID` 를 모든 로그 · 메트릭 라벨로 | 어느 인스턴스에서 난 일인지 구분이 안 된다 |
| R1 | **readiness 플래그** — 트래픽을 안 받는 인스턴스는 타이머 폴링 · 방 정리 · 스크래핑을 멈춘다 (§1.10) | Green 이 기동 즉시 Blue 가 건 타이머를 제 규칙으로 실행해, 트래픽을 갈라도 한 판이 두 버전에 걸친다 |
| R2 | graceful shutdown + 드레인 때 WebSocket 을 끊어 재연결을 유도 | 교체 순간 처리 중 요청과 연결이 그냥 끊기고, 기다리는 드레인은 판이 끝날 때까지 안 빠진다 |

### 5단계 — 블루-그린 (같은 EC2, 컨테이너 2개)

**진입 조건**: R1 · R2 · P4 · O0 이 끝났을 때. **여기서 돈을 쓰지 않는다.** `backend-blue` · `backend-green` 을 띄우고 Caddy 가 앞에서 전환한다. JVM 둘에 MySQL 까지라 **힙 제한을 걸고 메모리를 먼저 재 본다** — 1GB 가 모자라면 t3.small 승격이 선행이다.

| | 작업 | 지금 생기는 일 |
|---|---|---|
| C1 | `compose.yml` 을 백엔드 2개로, MySQL 포트를 사설로 | `ports: 3306:3306` 으로 **DB 가 인터넷에 열려 있다.** 보안 그룹이 유일한 방어선 |
| C2 | Caddy 업스트림 전환 + 쿠키 스티키 (`lb_policy cookie`) | SockJS XHR 폴백은 한 연결의 여러 요청이 같은 인스턴스로 가야 한다 |
| C3 | Flyway 단일 실행 또는 기동 순서 명시 | Green 기동이 Blue 가 도는 중 스키마를 바꾸고, 둘이 동시에 뜨면 경합한다 |
| C4 | Prometheus 타깃을 인스턴스별로 | `instance` 라벨 없이는 대시보드가 의미가 없다 |
| C5 | 헬스체크 liveness / readiness 분리 | 드레인 중 인스턴스가 재시작된다 |
| C6 | `deploy-backend.yml` 을 블루-그린 + 구환경 재편입으로 | `--no-deps backend`, `docker exec fungame-backend` 가 컨테이너 하나를 전제하고, 지금은 내렸다 올려 몇 초 끊긴다. 롤백도 이전 이미지를 다시 받아 띄운다 — 블루-그린이면 업스트림만 되돌리면 된다 |

**종료 조건**: 컨테이너 구성에서 A 에서 만든 방이 B 목록에 보이고 / B 로 들어온 정답이 처리되고 / A→B 재접속이
강제 퇴장당하지 않고 / 방 채팅이 양쪽 구독자에게 도달한다. **판이 도는 중에 한 인스턴스를 `docker kill` 해도
판이 이어지고 다음 라운드가 제시간에 온다. 그 인스턴스에만 붙어 있던 회원은 방에서 빠진다.** 배포 중 전환과 구환경 재편입을 거쳐도 진행 중인 판이 끊기지 않는다.

### 6단계 — websocket 모듈 분리

선행: P3. **연결은 모듈, 의미는 core.** 모듈은 게임을 모르고 core 는 STOMP 를 모른다.

| | 작업 |
|---|---|
| W1 | 모듈: 핸드셰이크 인증, `StompSessionRegistry`, 목적지 규칙, 구독 권한 조회, 스트림 수신 · 전달, 연결 · 끊김 이벤트 발행 |
| W2 | core: `*Notifier` 가 응답을 조립해 스트림에 넣는다. 끊김 유예 · 접속 상태 · 일일 활성처럼 연결이 도메인에서 갖는 의미는 core 가 판단한다 |
| W3 | 같은 회원이 여러 인스턴스에 붙었을 때 "마지막 세션이 끊겼는가" 판단을 모듈로 옮긴다. 기준은 §1.8 |

### 7단계 — 실제 EC2 증설

**진입 조건**: 지표가 한 대의 한계를 증명했을 때만. 그전에 **t2.micro → t3.small 상향과 스레드 풀 튜닝을 먼저**
시도한다. 첫 한계는 1GB RAM 일 가능성이 가장 높다.

| | 작업 |
|---|---|
| E1 | MySQL 을 앱 호스트에서 분리 (전용 EC2 또는 RDS) |
| E2 | ALB + 타깃 그룹 2개, 스티키 쿠키 |
| E3 | TLS 종료를 Caddy → ALB. 앱은 평문 8080 만 |
| E4 | 보안 그룹: 8080 · 3306 · 6379 는 ALB / 앱 SG 에서만 |

**비용** — 2대면 EC2 가 월 $8–9, ALB 는 12개월 뒤 월 $16~ 다. 더 싼 선택지는 app-1 의 Caddy 가 자기와 app-2 로
나누는 것(app-1 이 단일 장애점)과 Cloudflare 무료 플랜 오리진 2개(스티키가 유료라 SockJS 폴백을 끄고 WebSocket 만)다.

### 지표가 요구할 때만

| | 작업 | 신호 |
|---|---|---|

## 부록 A. 방별 스트림 키

지금은 전역 스트림 하나에 목적지를 필드로 싣는다. 쪼개면 인스턴스가 자기 구독자가 있는 방만 읽고, 트림이 방
단위가 되고, 엔트리 id 를 방별 순번으로 써 중복 전달을 걸러 낼 수 있다.

대가는 크다. `XREAD` 키 목록을 방이 생기고 사라질 때마다 바꿔야 하고, **"내가 어느 방의 구독자를 들고 있는가"
레지스트리**가 필요하며 그 등록이 한 번 새면 그 방만 조용히 메시지를 못 받는다. 로비 · 접속자 · 초대는 방 단위가
아니라 전역 스트림이 따로 남아 메커니즘이 둘이 된다.

**동시 진행 방이 수백 개로 늘어 역직렬화가 지표에 보이거나 / 한 방의 폭주가 다른 방의 보관 구간을 밀어내거나 /
중복 전달로 화면이 되감기는 것이 보고되면** 그때 한다. 도메인과 무관하게 가려면 `hash(destination) % N` 고정
샤드에 수신 측 로컬 필터를 얹는 쪽이 낫다. 소비자 그룹이나 방마다 Redis 커넥션 하나는 쓰지 않는다.
